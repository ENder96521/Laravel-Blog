# 個人技術部落格 專案企劃書

版本：v1.0
更新日期：2026-08-31

---

## 1. 專案概述

打造一個以「技術寫作」為核心的個人部落格，用於發表網頁工程相關的技術文章與新聞觀察。系統需具備完整的內容管理後台，並預留「每日技術文章草稿」的資料流程，未來可串接 AI 內容產生機制。

**核心目標**
- 提供簡潔、易讀的技術部落格前台，風格參考 Dev.to / Medium
- 透過 Filament 打造管理效率高的後台，供單一管理員使用
- 資料庫設計保留擴充彈性（未來可能開放多作者）
- 建立每日技術文章「草稿」流程的資料結構與人工審核發布機制
- 使用 CI/CD 自動化部署到 AWS EC2

## 2. 技術棧

| 項目 | 選型 |
|---|---|
| 後端框架 | Laravel（最新穩定版） |
| 後台管理 | Filament（Admin Panel） |
| 資料庫 | MySQL（與 Laradock 預設一致） |
| 開發環境 | Laradock（本機開發） |
| 前端渲染 | Laravel Blade + Tailwind CSS（輕量、無需另建 SPA） |
| 部署環境 | AWS EC2 |
| CI/CD | GitHub Actions |
| 版本控制 | Git / GitHub |

> 前端不採用 Vue/React 等 SPA 框架，理由：部落格為內容導向網站，SEO 與首屏載入速度優先，Blade + Tailwind 足以應付卡片列表、文章頁等頁面，且與 Laravel 生態整合度最高，維護成本低。若未來有互動需求（如留言即時更新），再評估局部導入 Alpine.js。

## 3. 功能需求

### 3.1 前台（訪客瀏覽）

- 首頁：文章卡片列表（Dev.to/Medium 風格），支援分頁或無限捲動
- 文章詳細頁：標題、封面圖、發布日期、閱讀時間估算、內容（Markdown 渲染）、分類/標籤
- 分類頁 / 標籤頁：依分類或標籤篩選文章列表
- 搜尋功能：依標題/內容關鍵字搜尋
- RSS Feed：供讀者訂閱（技術部落格常見需求，建議納入）
- SEO 基礎建設：meta title/description、Open Graph 圖片、sitemap.xml
- 響應式設計：手機、平板、桌機皆需清晰易讀
- **不含**：留言、按讚等互動功能（依需求先不做，資料庫設計保留擴充空間）

### 3.2 後台（Filament 管理）

- 管理員登入（Laravel 內建 Auth + Filament Panel，先做單一管理員角色）
- 文章 CRUD：
  - 標題、Slug（自動產生可手動覆蓋）、封面圖上傳
  - 內容編輯器：採用 Filament Rich Editor（所見即所得）
  - 分類（單選）、標籤（多選）
  - 狀態：草稿 / 待審核 / 已發布 / 排程發布
  - 發布時間設定（可排程未來時間自動上架）
  - SEO 欄位：meta description、OG 圖片（可選填，預設沿用封面圖）
- 分類管理：CRUD
- 標籤管理：CRUD
- 「每日技術文章草稿」佇列頁面（見 3.3）
- 儀表板：文章數量、草稿待審數量等基本統計

### 3.3 每日技術文章草稿機制（資料結構先行）

依你的決定，每日技術文章將串接 **Google Gemini API 免費層** 產生內容草稿。資料表與流程設計如下，確保未來若調整 AI 供應商或產生方式，也不需改動資料庫結構。

> **Gemini 免費層注意事項**：免費層有請求頻率與每日配額限制，實作階段需確認目前 Gemini API 免費方案的請求數/token 上限，並設計失敗重試與配額用盡時的錯誤處理（如當日排程失敗則記錄 log，不影響其他功能運作）。

**設計原則**
- 文章資料表新增來源欄位（`source`：manual / ai_generated / imported），方便未來追蹤文章是怎麼產生的
- 新增「草稿佇列」概念：AI 或任何自動化管道產生的文章，狀態一律為 `draft`，不會自動發布
- 後台提供獨立的「待審草稿」列表頁（可用 Filament 的狀態篩選器達成，不一定要開新資料表），管理員可在此預覽、編輯、核可發布
- 預留 `generation_meta`（JSON 欄位）：記錄產生時使用的來源提示詞、模型、參考連結等中繼資料，方便日後追溯與除錯，即使目前尚未決定產生方式

**發布流程**
```
[Laravel Scheduler 排程觸發] → 呼叫 Gemini API 產生文章內容
                             → 寫入 posts 表，status = draft, source = ai_generated
                             → 後台「待審草稿」列表出現
                             → 管理員預覽、編輯
                             → 手動點擊「發布」→ status = published，published_at 寫入
```

## 4. 資料庫設計（概念草案）

> 以下為概念層級設計，實作時 Claude Code 可依 Laravel 慣例調整欄位型別與索引。

**users**
- id, name, email, password, role（先固定 admin，欄位保留供未來多角色使用）, timestamps

**posts**
- id, user_id（作者，先固定為單一管理員，欄位保留供未來多作者使用）
- title, slug, excerpt, content（markdown 或 html）
- cover_image_path
- category_id
- status（draft / scheduled / published）
- source（manual / ai_generated / imported）
- generation_meta（json, nullable）
- meta_description, og_image_path
- published_at（nullable，排程發布用）
- timestamps

**categories**
- id, name, slug, timestamps

**tags**
- id, name, slug, timestamps

**post_tag**（多對多中介表）
- post_id, tag_id

> 留言功能未來若要加入，建議新增 `comments` 表（post_id, author_name, email, content, status, timestamps），並在 post 詳細頁預留留言區塊的版位，避免屆時改版面。

## 5. 前端設計方向

風格定位：**技術部落格風格**，參考 Dev.to / Medium 的卡片式列表與閱讀體驗，但避免直接複製既有網站的視覺語言，需依內容特性發展出自己的識別度。

**設計時應把握的原則（實作階段由 Claude Code 依此展開設計提案）**
- 排版以內容可讀性為核心：文章內文行寬控制在合理閱讀範圍內，避免一行文字過長
- 字體選擇需傳達「技術/工程」調性，但不落入純粹的等寬字或制式感過重的排版；標題與內文可用一組或兩組明確區隔的字體
- 首頁卡片列表需清楚呈現：標題、分類/標籤、發布日期、摘要，避免資訊過度堆疊
- 避免生成式網頁常見的樣板痕跡（如全大寫標籤、統一圓角卡片配隨機漸層裝飾、置中大字加漸層背景等），設計需扣合「個人技術寫作」這個主題本身
- 深色模式：技術讀者常見偏好，**列為 v1 必備功能**，前台需支援亮/暗模式切換（可依系統偏好自動判斷，並提供手動切換開關）
- 響應式：手機閱讀體驗需與桌機同等重視

> 實作階段會使用前端設計相關的技能指引，針對此網站主題產出具體的色彩、字體、排版提案，而非套用制式模板。

## 7. 部署架構（AWS EC2 + CI/CD）

**目標**：從專案初期就規劃 GitHub Actions 自動化部署，而非先手動後補。

**建議流程**
```
本機開發（Laradock） → git push 到 GitHub
                     → GitHub Actions 觸發：
                         - composer install
                         - 執行測試（若有）
                         - build 前端資源（如有 Vite）
                         - 透過 SSH 部署到 EC2（或使用 rsync / deployer）
                         - 於 EC2 執行 migrate、快取清理與重建
                     → 部署完成
```

**部署方案：AWS 免費方案（Free Tier）**

確定採用 EC2 免費方案，資料庫與圖片皆自架於同一台 EC2（不使用 RDS / S3）。此方案成本最低，但需注意免費方案的資源限制，實作階段需特別留意以下幾點：

- 免費方案 EC2 規格通常為 `t2.micro` 或 `t3.micro`（1 vCPU、1GB RAM），MySQL、PHP-FPM、Nginx 會共用這 1GB 記憶體，需要：
  - MySQL 做記憶體用量調校（如降低 `innodb_buffer_pool_size`）
  - 視情況加開 Swap 空間，避免文章量增加或流量突增時 OOM
- 免費方案儲存空間有限（EBS 通常為 30GB），圖片直接存在 EC2 本機硬碟，需規劃：
  - 上傳圖片時做壓縮/轉檔（如轉 WebP）以節省空間
  - 定期監控磁碟用量，避免文章與圖片增長後空間不足
- 因資料庫與圖片都在同一台機器上，屬於單點風險，建議規劃基本備份機制（如每日 cron 備份 MySQL dump + 圖片目錄，可先備份到同一台機器的另一個目錄，之後有餘裕再考慮異地備份）

**EC2 端需事先規劃的項目**（實作階段逐一確認）
- Web Server：Nginx + PHP-FPM
- PHP 版本與擴充套件需與 Laradock 一致
- MySQL：直接安裝於 EC2 上（免費方案，不使用 RDS）
- 圖片儲存：EC2 本機硬碟（`storage/app/public`，透過 symlink 對外提供）
**網域規劃**

目前尚無網域，需在部署前完成規劃。反向代理採用 **Nginx Proxy Manager（NPM）**，SSL 憑證透過 NPM 內建介面申請 Let's Encrypt 憑證（免手動跑 Certbot 指令），並可同時管理多個網域/子網域的轉發設定，未來若要擴充其他服務也方便。

免費網域選項（實作前可擇一嘗試，優缺點供你參考）：

| 方案 | 說明 | 注意事項 |
|---|---|---|
| eu.org 免費二級網域 | 長期免費、不需續期，功能與正式 TLD 相近，開發者社群常用 | 需人工審核，申請到核准時間較長，不確定何時能拿到 |
| ClouDNS Free Zone | 提供免費二級網域＋DNS 代管，申請即時生效 | 網域格式較不專業（如 xxx.cloud-ip.cc），部分平台（如 Cloudflare）不支援託管 |
| DuckDNS | 免費動態 DNS 服務，常用於家用主機/測試環境 | 格式為 xxx.duckdns.org，較適合測試用途，不建議作為長期部落格網域 |
| 付費真實網域（備案） | 如 Cloudflare Registrar、Namecheap，`.com`/`.dev` 年費約新台幣 300–500 元 | 若免費網域申請不順利或想要更專業的網址，這是成本很低的替代方案 |

> 建議：先申請 eu.org（免費但審核較久），同時準備 ClouDNS 或 DuckDNS 作為備案，若審核時間影響開發進度可先用備案上線，之後再換成正式網域。

**SSL 憑證與反向代理**
- 使用 Nginx Proxy Manager 統一管理對外網域的 SSL（Let's Encrypt）與轉發規則
- EC2 上需額外執行 NPM（建議以 Docker 方式運行，與現有 Laradock 開發習慣一致），由 NPM 將對外請求代理到 Laravel 應用的 Nginx + PHP-FPM
- www / 非 www 轉址規則於 NPM 介面設定

**環境變數與敏感資訊管理**
- `.env` 不進版控，透過 GitHub Actions Secrets 或 EC2 上手動設定

**Queue / Scheduler**
- 若未來要跑排程發布或每日 AI 草稿產生，需在 EC2 上設定 Laravel Scheduler（cron）與 Queue Worker（supervisor）
- 免費方案資源有限，Queue Worker 常駐程序會佔用記憶體，建議先以 Scheduler + cron 排程觸發、輕量任務跑完即結束的方式設計，避免長駐 process

**備份規劃**
- 頻率：**每週備份一次**
- 保留：**保留最近一個月**（約 4–5 份備份，超過即可清除舊備份）
- 內容：MySQL dump + 圖片目錄（`storage/app/public`）
- 方式：透過 cron 排程執行備份腳本，備份檔案先存放於 EC2 本機另一目錄；若免費方案儲存空間吃緊，需評估備份檔案的保留策略（如只保留最新 4 份，超過自動刪除最舊的）
